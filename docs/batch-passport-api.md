# Паспорт партии

`GET /api/v1/batches/{id}/passport` возвращает готовый `BatchPassportDto`.
`id` — UUID партии. Для frontend предусмотрены proxy
`GET /api/batches/{id}/passport`, типы и функция `fetchBatchPassport`.
Существующие поля DTO и идентификаторы сохранены.

## Что входит

- `batch`: сведения о партии, происхождение, кросс, птичник и цех.
- `ageDays`, `ageBasis`: возраст от даты вывода; если её нет — от посадки с предупреждением.
- `kpi`: поголовье, расчётная смертность, сохранность и счётчики.
- `kpis`, `microclimate`: основные показатели и микроклимат.
- `lighting`: освещённость и соблюдение светового режима.
- `consumption`, `mortality`: показатели корма, воды и смертности.
- `incidents`, `notifications`, `tasks`, `attachments`: связанные с партией записи.
- `aggregates`: количество инцидентов, критичных инцидентов, открытых задач и отклонений.
- `status`, `summary`, `dataQuality`: итоговая оценка и сведения о неполных данных.

По показателям рассчитываются среднее, минимум, максимум и последнее значение.
Телеметрия берётся из InfluxDB за период от посадки до текущего времени или закрытия
партии, только по назначенным датчикам. Разные единицы измерения не объединяются.
Отклонение — показание за пределами заданного диапазона, а не отдельный инцидент.

## Настройки и ограничения

Миграция V24 добавляет привязку датчиков, нормы, дату вывода, часовой пояс и настройки
светового режима. `GET/PUT /api/v1/batches/{id}/passport-settings` читает/заменяет
настройки: `timeZone`, `farm`, `hatchDate`, `lightingHouseId`, `sensorIds`, `metricNorms`.
Норма содержит `type`, `unit`, `minimum`, `maximum`; нужна хотя бы одна граница.
Нормы действуют на весь период; возрастные программы автоматически не рассчитываются.

Инциденты, задачи и уведомления выбираются по `batchId`, вложения — через инциденты.
Без назначенных датчиков, норм и связей соответствующие данные будут неполными.
Корм и вода возвращаются в исходных единицах: скорости не превращаются в суммарный
расход. `kpi.mortality` — разница начального и текущего поголовья, без учёта переводов.

## Статус и ошибки

Приоритет: `CRITICAL` — активный критичный инцидент или критичный световой режим;
`WARNING` — активный инцидент, открытая задача или отклонение; `UNKNOWN` — данных
недостаточно; `NORMAL` — данные полны и перечисленных проблем нет.
В прежнем поле `summary.status` нормальному состоянию соответствует `OK`.

Неизвестная партия: 404. Некорректные настройки: 400. Неполный паспорт: 200,
`dataQuality.complete=false`, причины в `issues`, неизвестные числа — `null`.
При недоступности InfluxDB сохраняются разделы из PostgreSQL и добавляется причина
`TELEMETRY_UNAVAILABLE`. Ошибка PostgreSQL не маскируется пустым паспортом.

Структура DTO подготовлена для согласования с frontend-разработчиком.
Экран паспорта в рамках этой backend-задачи не реализован.

## Подключение frontend

1. Получить UUID выбранной партии из `GET /api/v1/batches` через серверный слой
   приложения. Не использовать статический ID из демонстрационных фильтров.
2. В браузере вызвать готовый клиент; типы находятся в `frontend/lib/batch-passport.ts`:

```ts
import { fetchBatchPassport } from "@/lib/batch-passport"
import type { BatchPassportResponse } from "@/lib/batch-passport"

const passport: BatchPassportResponse = await fetchBatchPassport(batchId)
// passport.batch — шапка, passport.microclimate — показатели,
// passport.aggregates — счётчики, passport.status — общий статус.
```

3. Предусмотреть загрузку, ошибку запроса и успешный ответ с неполными данными.
   `fetchBatchPassport` выбрасывает ошибку при HTTP не 2xx; дополнительные запросы
   для сборки паспорта не нужны. При смене партии можно отменить предыдущий запрос,
   передав `AbortController.signal` вторым аргументом.
4. `null` отображать как «Нет данных», сохраняя настоящий `0` (использовать `??`,
   не `||`). Показывать причины из `dataQuality.issues`, даже если общий статус
   `WARNING` или `CRITICAL`. Не заменять недостающие значения демонстрационными.

Для карточки показателя использовать `type` и `unit`, а не индекс массива:
один тип может иметь несколько единиц измерения. `kpi` содержит общие счётчики,
`kpis` — измеряемые KPI. `batch.status` — стадия жизни партии, верхний `status` —
оценка состояния. Для возраста при `ageBasis=PLACEMENT_DATE` подписать «Дней с посадки».
Даты партии без смещения относятся к `batch.timeZone`; `generatedAt`, даты телеметрии
и границы `period` содержат UTC. Для вложений использовать существующий proxy
`/api/incidents/{incidentId}/attachments/{id}/content`.

Ниже сокращённый фрагмент неполного паспорта, а не полный JSON для подстановки.
Остальные разделы также присутствуют в реальном ответе; точная структура описана
типом `BatchPassportResponse`.

```json
{
  "schemaVersion": "1.0",
  "generatedAt": "2026-10-12T08:00:00Z",
  "ageDays": 11,
  "ageBasis": "PLACEMENT_DATE",
  "microclimate": [
    {
      "type": "TEMPERATURE", "unit": "C", "sampleCount": 120,
      "average": 23.5, "minimum": 21.0, "maximum": 27.0,
      "latest": 24.0, "latestAt": "2026-10-12T07:59:00Z",
      "norm": {"minimum": 18.0, "maximum": 25.0},
      "deviationCount": 3, "status": "WARNING"
    }
  ],
  "aggregates": {
    "incidentCount": 2, "criticalIncidentCount": 1,
    "activeCriticalIncidentCount": 0, "openTaskCount": 1,
    "deviationCount": 3, "deviationsComplete": false
  },
  "status": "WARNING",
  "dataQuality": {
    "complete": false,
    "issues": [
      {"code": "HATCH_DATE_MISSING", "field": "batch.hatchDate",
       "message": "Age is calculated since placement, not hatching"}
    ]

```

`issues.message` сейчас на английском; для русских подписей frontend может
сопоставлять стабильный `code` с переводом, оставляя запасной текст для новых кодов.

## Что согласовать перед интеграцией

- С frontend: подходят ли поля DTO, подписи, отображение `null`, частичного паспорта
  и возраста от посадки. Подтвердить контракт; он пока подготовлен, а не согласован.
- С ответственным за требования: повышает ли любая открытая задача статус до
  `WARNING`, должны ли исторические отклонения влиять на статус весь период партии.
  Сейчас оба правила включены.
- Подтвердить нормы показателей и достаточно ли статистики расхода в исходных
  единицах. Суммарные килограммы/литры и возрастные нормативы требуют отдельного
  расчёта и сейчас не реализованы.
